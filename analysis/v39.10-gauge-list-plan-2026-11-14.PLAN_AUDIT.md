**A2 (INFO, verified). `fetchNWSForecasts()` before and after.**
- **Before:** It maps `NWS_LIDS` (17 entries, `constants.js:160-178`) into 17 `fetchSingleNWSForecast` promises (each `.catch(() => null)`) and 17 `fetchFloodCategory` promises. It awaits both arrays together. It writes `data[id].floodCategory` for every non-null category result. Then it runs the forecast loop: skip null results and ids with no `data` entry, count, set `data[id].forecast`, and when there is a 24 h or 48 h value compute direction and rate from `data[id].q`. Finally it logs.
- **After:** The same, minus the category array and loop, with `const forecastResults = await Promise.all(forecastPromises)`.
- The text from `// Apply forecasts to data` to the end (lines 70-95) is unchanged, so `forecast` and `trend` get the same values for the same `data` state.
- The one difference is timing: the loop now runs as soon as the forecasts land, not when the slower of the two arrays lands. It reads `data[id].q` and the live `data` binding at that earlier moment. In the normal case the values are identical. If a refresh runs `processData` during the window, the target object can differ. That race existed before too, so it is not a regression.
- `fetchWithTimeout` is still used by `fetchSingleNWSForecast` (line 26), so its import stays.

**A3 (INFO, verified). Callers and timing.**
- The only caller is `src/data/fetch.js:555`. It is fire-and-forget: `.then(() => emit('nws:arrived'))` and `.catch(warn)`, after `setFetchSettled(true)` and `emit('data:updated')`, and not awaited by `fetchData`. `src/init.js:49` wires `nws:arrived` to `updateUI`, which is idempotent.
- `src/data/refresh.js` does not reference it.
- Each request has its own `AbortController` and 5 s timer (`fetch.js:77-92`). There is no shared abort or deadline and no request counter.
- Resolving earlier only moves the `nws:arrived` repaint earlier. If the NOAA host is on HTTP/1.1 (6 connections per host), forecasts no longer queue behind the 17 category calls. That is a benefit and is not verified.

**A4 (INFO, verified). No test is affected.**

- The refresh tests (`startup-refresh-behaviour.test.mjs:85-90`, `data-freshness.test.mjs:384`, `:634`) stub `fetch` and return `no()` for anything other than USGS and Edwards Ferry. Their timer counts filter on `ms === 60000` only (lines 103, 325, 340, 406, 619), so 17 fewer 5000 ms timers change nothing.
- `startup-refresh-behaviour.test.mjs:117` does not listen for `nws:arrived`.

**A5 (INFO, verified). "Service worker config unchanged" holds.**
- `config/runtime-caching.mjs` has no category-specific route. Both URL kinds go through the general `api\.water\.noaa\.gov` regex (route `pp-data`, NetworkFirst, 4 s, `maxEntries: 32`). The CSP still needs `api.water.noaa.gov` for the forecast.
- Side effect, positive and unverified: up to 17 category entries no longer compete for the 32 `pp-data` slots with forecasts, creeks, Edwards Ferry, water temperature and proxy entries, so fewer useful fallbacks get evicted.

**A6 (MINOR). The two URL kinds are distinguishable, but test 5 must say exactly how.**

## C. Item 2 (header cell as tap target)

**C1 (INFO). Traces with the planned code.** Delegated handler at `gauges-ui.js:161-182`, dismiss handler at `34-47`, with `.col-info-cell` in both:

| Action | Result |
|---|---|
| Mouse click on the "Next 24h" label | The target is the cell div. `closest('.col-info-cell')` returns the cell and `querySelector` returns the button. It toggles and sets `aria-expanded` to true or false. The document click sees a target inside the cell and does not dismiss. Correct. |
| Click on the icon | Same, through the button's ancestor cell. Same as today. |
| Click on "Gauge", "CFS" or "Hrs→LF" | No cell, no `.branch-hd`, so the delegated handler does nothing. The document click closes any open bubble and sets `aria-expanded` to false. Same as today. |
| Click on a gauge row | Same as the row above. A click on a branch header also toggles the branch, as today. |
| Enter or Space on the focused button | A synthetic click with the button as target. Toggles as today. Escape still closes. |

**C2 (INFO). Phone tap on the label.**
- `pointerdown`: the target is inside the cell, so no dismiss. `click`: toggle. Switching from the other label: `pointerdown` does nothing, then `click` closes all and opens this one.
- Today, a tap on the label closes an open bubble on `pointerdown` and does nothing on `click`. The new behaviour is the intended improvement.

**C3 (INFO). A tap on the open bubble is unchanged.**
- The bubble is the button's `::after`, `position: absolute`, anchored to the sticky `.gauge-header` (the comment at `main.css:445-446` says `.col-info` is "Not position:relative on purpose"). It sits at `top: 100%` across the header, so it lies over the branch headers and gauge rows below, not over a header cell.
- With `pointer-events: none` the tap reaches the row or branch header underneath: `pointerdown` dismisses, and the click may toggle a branch. Same as today; the cell does not change this.
- **Constraint to add to the plan:** `.col-info-cell` must not get `position: relative`. Otherwise the bubble would anchor to the 78/82 px cell. The existing guard at `map-removed.test.mjs:163` only checks `rule('.col-info')`. **Fix:** test 4 also asserts that the `.col-info-cell` rule has no `position`.

**C4 (MINOR). The plan's reason for `cursor: pointer` is wrong; the rule is harmless.**
- WebKit's missing-click problem applies to delegation on `document` or `body`. The `#branches` container has its own click listener, so iOS should already send the click there.
- The branch headers cannot prove this either way, because `.branch-hd` already has `cursor: pointer` (`main.css:412`).
- The rule stays useful as insurance and as a desktop affordance. The button keeps `cursor: help`, because the more specific rule wins.
- Side effect: iOS shows its grey tap highlight on the whole cell. The repo sets no `-webkit-tap-highlight-color`. This is cosmetic, and branch headers already do the same.
- **Fix:** reword the plan's justification to "harmless insurance". Leave the rule.

**C5 (MINOR, acceptable). Accessibility.**
- The cell becomes a clickable div with no role. That is acceptable because it duplicates a real control: the button keeps its focus ring, `aria-expanded` and `aria-label`.
- A VoiceOver user who activates the "Next 24h" static text will also toggle the bubble. Harmless.
- No regression for keyboard use.

**C6 (MINOR). Other header bindings and the sticky tab bar.**
- No sorting or other listener on `.gauge-header`. Search for `gauge-header` and `branches` in `src` finds only `gauges-ui.js` and `main.css`.
- On phones, `.tabs` (`main.css:114`) and `.gauge-header` are both `position: sticky; top: 0; z-index: 5` inside the single `#sidebar` scroller. The header comes later in the DOM, so where they overlap it paints on top.
- Taps there already missed the tab bar before this change. Now they would open a bubble instead of doing nothing.
- This is pre-existing and listed as plan Risk 4. It cannot be verified without a phone. Add it to the C6 phone-check row.

## E. Tests in the plan

**E2 (MAJOR). Test 6's "exactly one request per entry of `NWS_LIDS`" holds only for a specific stub.** `fetchSingleNWSForecast` tries up to four URLs in order and stops at the first that parses.
- **The count is 17 only if** every gauge's first URL returns a parseable forecast. That means `ok: true`, a `text()` method, points with `validTime` 18-30 h and 42-54 h after `Date.now()`, and a positive `secondary`.
- The plan also wants a gauge with no forecast (implied by "a gauge with a forecast"). Such a gauge makes four forecast requests.
- **Fix:** assert zero requests whose pathname matches `^/nwps/v1/gauges/[^/]+$`, and assert the request count per LID (1 for gauges with a stubbed forecast, 4 for gauges without).
- **Seeding:** export `setData` (or `data`) from the same esbuild bundle as `fetchNWSForecasts`. A separately imported store module is a different instance, and the test would pass vacuously with an empty `data`, because the loop skips ids not in `data`.
- Feasibility is fine. `data-freshness.test.mjs:53-57` and `startup-refresh-behaviour.test.mjs:27-34` already bundle `fetch.js` (which `nws.js` imports) in Node and stub `fetch`. The real `setTimeout` in `fetchWithTimeout` is cleared on resolve.

- **Stronger, optional:** also seed one gauge with `q` and expected `rate` and `direction` per branch (up above 0.02, down below −0.02, stable, and the 48 h fallback). Nothing tests `nws.js` today (A4), so this would be the first coverage.
