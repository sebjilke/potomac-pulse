# Audit of PLAN_v1.md (onset study, TODO D20)

Auditor: independent plan auditor (Opus), read-only, 2026-11-25. I did not write the plan.
Scratch scripts and outputs: `/private/tmp/claude-503/-Users-sebjilke/252f7c3c-5965-4854-a165-14468fc066da/scratchpad/onset_plan_audit/` (`power.mjs`, `power2.mjs`, `power_out.json`, `p2.json`). They read `replay_B/shadow_L.csv`, `replay_B/bins_L.csv` and the v39 input file, import the production correction helpers, and compute NO error of any candidate rule. They count hours and measure how far each candidate would move the shown number (no truth used).

## Verdict

**PROCEED AFTER CHANGES.** The core idea is sound: learning in production and in the replay never reads the applied correction, so one replay can serve all rules. But the plan has one defect that would stop the run on its first row (rounded raw), two design gaps that would make a PASS hard to interpret (no shrinkage control; the rule is not one-signed), and a transfer problem (the replay's "six-hour change" is a four-hour change, and the browser computes the state differently). None needs a new design; all need text changes before the specification is written.

## Findings

### F1. MAJOR. Check (c) and the rule itself need the unrounded raw estimate; the plan does not say so
Evidence: `makeGFPrediction` returns `rawFinalCFS: Math.round(rawFinalUnclipped)` and `correctionApplied: Math.round(correction)` (`scheduled-update.js:1106`, `:1108`); `predictedCFS` is `Math.round(correctedFinal)` computed from the unrounded raw (`:1104`). The shadow file holds only the rounded values. Using the rounded raw, I recomputed `round(min(raw - corr, 1.2 x lfQ))` with the exact production correction: it differs from `predictedCFS` on 27,629 of 128,595 predicted hours (21.5%). The correction itself, looked up with the rounded raw, differs from `correctionApplied` by 1 cfs on 1,869 hours and by 524 cfs on one hour (2016-02-19 07:00, raw rounds to exactly 50,000 and the bin flips). With "one failing row stops the study", the run would stop at once.
Recommendation: the tool logs `trace.rawUnc` (the unrounded raw) and the unrounded `corrR`, `corrS`, `corrF`, `trace.corr`. Check (b) compares the state's correction to `trace.corr` exactly. Check (c) and every rule use the unrounded raw. The "below 25,000 cfs" test uses `flowBin` (that is, `getFlowBin` of the unrounded raw), never the rounded raw.

### F2. MAJOR. No control separates the onset effect from plain shrinkage of two noisy numbers
Evidence: each cell is an EMA with alpha 0.3 (`model.js:497`, `:793`). Its variance is alpha/(2 - alpha) = 0.18 of one residual's variance, the same as a mean of about 6 observations; it tracks the last few validations. The earlier audit found the same cell at +571 cfs in one arm and -602 cfs in the other after one December rise (`replay_lag_audit.md`, section E). A blend of the rising and steady values averages two such noisy numbers. It can lower the error for that reason alone, whatever the size of the rise. A PASS for m* would then be read as "gentle onsets need the steady value" when the cause is "the rising value is noisy".
Recommendation: add one reference rule that does not use `d6`: a constant blend `w = 0.5` on every rising hour below 25,000 cfs (and report the three-state mean as well). Fix in advance how it is read: if the constant blend does as well as m* in the test years (difference of mean `d` within 0.10 points, or its interval covers m*'s value), the verdict text must say the gain is not shown to come from the onset. Also add to A1 a column "hours since the rising cell was last updated" (from `bins_L.csv`), so that staleness of the rising value can be told apart from the size of the rise.

### F3. MAJOR. The rule is not one-signed; the plan's question assumes it is
Evidence: the plan's question 1 and its hypothesis say the rising value "takes off too much". Over all rising hours below 25,000 cfs, replacing the rising value by the steady value raises the shown number in 4,720 of 8,148 test hours (58%) and LOWERS it in the rest (design years: 3,951 of 7,052, 56%). For m = 2, the rule moves the shown number down on 1,781 of 4,514 affected test hours (39%). The plan's own section 2 point 8 shows it: at 0 to 3,000 cfs the steady value (+337) is larger than the rising value (+311). On those hours the rule pushes the number toward the unsafe side (too low), which A6 and A7 identified as the main harm on rising water.
Recommendation: in A1 and in step B, split every table by the sign of `corrR - corrS` at that hour (rule raises / rule lowers the shown value). Add a guard to the decision rule: on affected hours where the rule lowers the shown value, mean `d` is not above 0 (point estimate) and the share 15% or more below the truth does not rise. Rewrite question 1 as two-sided.

### F4. MAJOR. The replay's "six-hour change" spans four hours; production's spans about five; the browser uses yet another rule
Evidence: `getFlowState` compares `por.q` with the last history entry at or before `Date.now() - 6 h` (`model.js:469-480`). In arm L the newest Point of Rocks value is the row at t - 2 h (`ci_backtest_harness_lag.mjs:358-360`), so the change spans t - 2 h to t - 6 h. I reconstructed the past reading for every predicted hour of `replay_B/shadow_L.csv`: the span is exactly 4 h on 126,688 of 128,595 hours (98.5%), and my reconstructed state equals the file's `flowState` on all 128,595. In production at minute :00 the newest reading is about 66 min old and the past reading is at about now - 6 h, so the span is about 4.9 h (README of replay_lag, simplification 1; the earlier audit's figure "5 h lagged" for the replay does not match this count). Arm F spans 5 h. A given rate of rise gives a `d6/thr6` about 20% smaller in the replay than in production, so m* does not carry over one to one. Also, the browser's state does not come from `getFlowState`: it comes from `getPoRRiseRate` (`src/estimation/great-falls.js:176-216`: median-of-record endpoints, a span anywhere from 3 to 9 h, and an NWS fallback at `:464` where no `d6` exists). The plan's section 2 point 1 calls `src/model/shared-model.js` the "browser twin"; that copy exists but the browser does not use it for the state.
Recommendation: (a) say in the plan that `d6` in the replay is a 4 h change; (b) pre-register a sensitivity run with arm F (5 h span) on the same tool, with m* fixed from arm L's design years, report-only; (c) consider defining the hand-over on the rate `d6 / span` (cfs per hour relative to the threshold per hour), which transfers across spans; (d) section 9 "what follows a verdict" must state that the browser path (robust endpoints, NWS fallback) is untested and that a build plan must define `w` for the fallback (for example `w = 1`, production behaviour).

### F5. MAJOR. The hypothesis came from the same record the test uses
Evidence: D20's 2,987 pairs cover 2011 to 2026 (`replay_lag_FINAL.md`), so the test years 2020 to 2026 helped suggest the rule's form. The plan admits this (section 11). The project's own precedent is stricter: A7 closed with "a new idea needs a new plan and new data (rises after 2026-11-09) or a separate audited design" (`rising-limb-travel-verdict-2026-11-11.md`).
Recommendation: keep the split (it protects `m`), but make a PASS lead only to a prospective check, not to a build plan: score the rule on rises after 2026-11-25 from `tick_log` (raw, state, cell and correction are logged since v39.2, `scheduled-update.js:2864`) and the daily `bin_snapshot`, with the threshold and m* frozen now. State the minimum number of new rising hours before it counts.

### F6. MINOR. "Production equals m going to 1" does not hold at exact ties
Evidence: production calls an hour rising when `|change| >= threshold` (`model.js:487`). At `d6 = thr6` the formula gives `0 / 0` when m = 1 (NaN, and `clamp(NaN)` is undefined in JS, Python and R alike), and `w = 0` for every m > 1. Exact ties are common because Point of Rocks values are round numbers and the threshold is exactly 100 below 5,000 cfs: 1,256 of 128,595 predicted hours have `|d6| = thr6` exactly.
Recommendation: define production as its own rule (`w = 1` on every rising hour), not as the limit. State that ties get `w = 0` under every candidate, and report how many affected hours are ties.

### F7. MINOR. Rounding must be JavaScript's, and the analysts should not re-derive it
Evidence: production rounds with `Math.round` (half up). Python's `round` and R's `round` round half to even. Two blind analysts recomputing shown values from logged columns will differ from production on any exact .5.
Recommendation: either the tool writes the shown value of every candidate (computed in JS through the same arithmetic as `applyGFCorrection`, no truth needed), or the specification prescribes `floor(x + 0.5)` in both languages.

### F8. MINOR. The size criterion depends on `m` and is diluted by trivial changes
Evidence: "affected" grows with m (test years: 3,386 / 4,514 / 5,733 / 6,643 hours for m = 1.5 / 2 / 3 / 5). Many affected hours move by less than 1% of the raw estimate: 53% at m = 1.5, 42% at m = 2, 33% at m = 3. A2 picks m on all rising hours below 25,000 cfs; B judges on "affected". The two can disagree.
Recommendation: state the primary size criterion on the fixed population "rising hours below 25,000 cfs" (for m = 2, -0.50 on affected corresponds to about -0.28 on that population, since affected hours are 55% of it), or keep "affected" but report the dose (mean |change of the shown value|) next to mean `d`. Reword the FAIL line as "mean `d` above -0.25".

### F9. MINOR. Criterion 6 is true by construction
It checks that the rule did not touch hours at 25,000 cfs and above, which the formula guarantees. Keep it as a tool check, not as evidence. The step that the rule creates at 25,000 cfs is real: in the test years 148 rising hours at 25,000 cfs and above have `d6 < 2 thr6` (design years 477); they keep the full rising value while their neighbours below 25,000 cfs get the steady value. Report the size of that step, not only the count.

### F10. MINOR. Criterion 2 uses a point estimate; the smallest cell is thin
Evidence: test-year rising hours below 25,000 cfs per cell: 0-3,000: 1,587; 3,000-6,000: 2,586; 6,000-12,000: 2,567; 12,000-25,000: 1,408 (affected at m = 2: 498). All four pass the 300-hour floor, so all four are judged. A 2% relative change on a cell MAE of several percent is about 0.1 to 0.2 points, which is the order of the noise in the smallest cell.
Recommendation: keep it, but report each cell's interval, and say in advance that a cell failing with an interval that covers 0 counts toward UNCLEAR, not FAIL (that is already the plan's logic; say it explicitly).

### F11. MINOR. The tool must re-implement the six-hour lookup; check (a) only checks the state
Evidence: the model does not expose the past reading (`trace` has `rst` from `getPoRRiseRate`, not the `getFlowState` past reading; `scheduled-update.js:975`). Check (a) passes for any `d6` with the right sign and size class.
Recommendation: also log `pastTs` and `pastCfs` and check that `pastTs` is the last history entry at or before t - 6 h, and that `porQ` is the last history entry (the existing `assertHistory` does the latter).

### F12. MINOR. Freeze the candidate list before A1
A1 computes, in the design years, the error of the shown value with the steady value by `d6` group. That table invites a new rule form. Say that no candidate is added or reshaped after A1; a new form needs a new plan.

### F13. MINOR. Bootstrap blocks
Months are a reasonable cluster (all 83 test months contain affected hours at every m). But the gap `corrR - corrS` persists across months until the rising cell is re-learned, so months are not independent. Pre-register quarters and rise episodes as report-only sensitivities, as the earlier audit did.

### F14. MINOR. Factual corrections to sections 2, 3 and 5 (details under question 8).

## Answers to the plan's questions

**1. Does anything in learning depend on the applied correction?** No, in both places. Production: the residual learned is `rawCFS - actualCFS` (`scheduled-update.js:1242-1245`); Check 1 uses EF and the truth, Checks 2 and 3 the truth, Check 4 the raw error (`:1327`), Check 5 the raw error against the bin (`:1400`); the bin key is the stored `flowBin` and `flowState` (`:1359`); the pending slot decision uses only `validationDue` (`storePrediction`, `:2012-2034`), which depends on the travel time, not on the correction. Replay: `validateAt` uses `p.raw` for the error and the gate; `p.corr` only for `errPctCorr` (`ci_backtest_harness_lag.mjs:540`, `:558`); the slot stores the same record. One replay serves all rules. Detail under question 9.

**2. Can `d6`, `thr6` and the three corrections be logged exactly?** Yes, with F1 and F11. The correction helpers are pure and the bins object at the model call is the one the tool holds (`makeRecord` runs after the hour's learning step, `:688-693`). My reconstruction outside the tool reproduces the state on 128,595 of 128,595 hours, and the applied correction to within rounding on all but one hour (the one flip is the rounded-raw artefact of F1). Compute `corrR`, `corrS`, `corrF` inside `makeRecord` right after `predictFn`, with the unrounded raw.

**3. Is arm L the right stand-in?** It is the closest of the existing arms for input age, and it has a regression target. It is not right for the state rule's span (4 h against about 4.9 h; F4). The earlier replay's README gives the real input ages: L about 97.5 min, production about 66 min (the plan says "about one hour"). Keep L as primary; add arm F as a pre-registered report-only sensitivity.

**4. Is picking `m*` sound? Candidates? Steady always?** The split is sound for one number (see question 11). The candidate list covers the range of `d6/thr6` well: in the test years rising hours below 25,000 cfs fall 31% at 1 to 1.5, 19% at 1.5 to 2, 21% at 2 to 3, 16% at 3 to 5, 9% at 5 to 10, 4% above 10. "Steady always" is the m = infinity end of the same family; treat it as a fifth candidate, or say in advance what it means if it beats every finite m in the design years (then the rising cell adds nothing below 25,000 cfs and the "onset" framing is wrong). Add the constant-blend control (F2).

**5. Decision rule and thresholds; missing harm check.** See question 12 for the thresholds. Missing harm checks: the hours where the rule lowers the shown value (F3); the shrinkage control (F2); the display step at 25,000 cfs (F9). Not needed: falling and steady hours are untouched by construction under the primary rule.

**6. Too few affected hours?** No. Test years, m = 2: 4,514 affected hours in 83 months; 2,319 and 2,195 in the two halves; 1,732 in 15 Sep to 15 Dec and 2,782 in the rest; per cell 1,126 / 1,572 / 1,318 / 498. Design years: 4,000. The limit is the dose, not the count: the mean |change of the shown value| on affected hours is 2.05 points (m = 1.5), 2.53 (m = 2), 3.02 (m = 3), 3.58 (m = 5) in the test years. Mean `d` cannot exceed that in size.

**7. Missing approach.** (a) The constant-blend control (F2). (b) An application-only minimum duration: apply the rising value only from the k-th consecutive rising hour, steady value before. It needs no change to learning and tests the "later rising call" idea that section 12 defers to a costly second stage. (c) A rate-based hand-over (F4c). Add at most one of (b) or (c) as a candidate, picked in the design years with the others, to keep the comparisons few.

**8. Factual claims in sections 2, 3 and 5 that do not hold or need a correction.**
- 2.1: "browser twin `src/model/shared-model.js`": that copy exists (`:353`) but the browser's state comes from `getPoRRiseRate` in `src/estimation/great-falls.js:176-216` and `:464`, with robust endpoints, a 3 to 9 h span and an NWS fallback. Also: the lookback is "the last reading at or before six hours before the clock", not "the reading six hours ago"; in the replay it is a 4 h change (F4).
- 2.4: holds. Add that nothing else in learning reads the correction (question 9).
- 2.5: holds; the ±12% band is multiplicative (B/1.12 to 1.12 B, `model.js:646-647`), not symmetric.
- 2.6: "differ only in how fresh the readings are": they also learn their own bins separately and their state spans differ (5 h against 4 h). The "slow upstream change" evidence is by `pct`, the change since the time-shifted reading (about a travel time back), not by `d6`; it is indirect support for a `d6` rule.
- 2.7: "failed in each half of the record alone": the documents say it "would read INCONCLUSIVE" in either half (upper ends 0.512 and 0.586), not FAIL. The other points hold; I confirmed the auditor's scratch scripts (`audit6`) are gone (only empty `__pycache__` and `dl` folders remain).
- 2.8: not checked (no outside requests). The values must come with the time read and the bin counts.
- 3, floor gate row: holds (`flow-state-floor-gate-findings-2026-06-18.md`: rising cell +2.33 MAE, 56.6% of steady-to-rising flips worse).
- 3, C45 row: the re-open condition also says "gate it with `analysis/c45_gate.mjs`" (TODO.md, C45 Phase 2). The plan uses another tool; say why.
- 3, A6/A7 row: "because the 120% cap governs the number" is the verdicts' reading, marked there as inference, not a test result.
- 3, D23 row: "about 3 times a day in autumn" was measured over 8 and 4 days in November 2026 only (TODO D23), not over past autumns.
- 3, last line: "fewer rising calls" was in effect changed once: v35.0 widened the window from 2 h to 6 h because the 2 h window called about 99% of baseflow steady (CHANGELOG v35.0). The span of the change is a known lever; that supports F4.
- 5: "about one hour old": about 97.5 min in arm L (README simplification 1). The harness's default `--in` is the v361 file (`ci_backtest_harness_lag.mjs:53`); the copy must be run with `--in=` the v39 file, as replay_B was.

**9. Can "learning never depends on what is applied" be broken?** I found no path. Production paths from the shown value: the headline accuracy (`:1777`), the 7-day validation history (`:1907`), the LF-residual advisory's pairs (`:1993`), the soft-outlier and hard-flag log rows (`:1617`, `:1432`), the 24 h graph history (`storeGFHistory`, `:512`), `tick_log`. None feeds the bins, a flag, the slot or the next hour's estimate. The LF-residual advisory latches on a shown error of -15% or worse; the rule would change when the advisory shows and the confidence label, which the study does not model. Criterion 5 measures the same threshold; say this link in the plan. The cap: display only, never read by learning (`model.js:705-721`; A4b). The anomaly gates: raw or truth only. The slot: depends on `validationDue`. Shadow models: seeded from the raw (`:3546-3552`). Replay: hybrid mode as under question 1; advisories, stage bins and forecasts are not replayed. The one thing that does depend on the applied value is the test of the plan itself: the "affected" set is defined by the shown values. That is outcome-blind and fine.

**10. Is the rule well defined for every hour?** Mostly. Zero or negative: `thr6 >= 100`, so no division by zero for m > 1; on rising hours `d6 >= thr6 > 0`. For the "both sides" reference the formula must use `|d6|` (as written, `d6 < 0` on falling hours gives `w = 0` always). m = 1: undefined at ties (F6). Missing history: state is steady (fewer than 8 entries: 571 predicted hours), so the rule does not apply; fine. Sparse cells: handled by the production lookup, but note that a rising cell with fewer than 5 counts already blends toward a pooled value that includes the steady cell (`model.js:565-617`), so the blend is partly a blend with itself; report the count of affected hours with a sparse rising or steady cell. Flow-range smoothing: both values are interpolated at the same raw, so the result is a bilinear blend, continuous in flow; fine. The 25,000 cfs step: production already steps there; the rule changes the size of the step for gentle rises (F9). Rounding: F1, F7. "Production = m going to 1": not exactly (F6).

**11. Design/test split, bootstrap, comparisons.** The split is sound for choosing `m`: the rule never changes learning, so the test years' corrections are the same under every rule, and no information about the rule leaks through the cells. What the split does not protect is the rule's form (F5). Months as blocks: acceptable, with quarters and rise episodes as sensitivities (F13). Comparisons: one number picked from four in the design years, one test, and a conjunctive decision rule; the risk of a false PASS is low. The risk of a false FAIL or UNCLEAR is higher (five conjunctive checks, three of them point estimates). That is acceptable for a change that would be a MAJOR release.

**12. Thresholds and power.** Counts above (question 6). The -0.50 point threshold on affected hours asks the rule to capture about 20% of its own dose at m = 2 (2.53 points mean |change|), for example right on about 60% of hours and wrong on 40% with equal sizes. That is attainable only if the D20 mechanism is strong; given F3 (39% of affected hours move down), it is not soft. In headline terms, -0.50 on 4,514 of 59,448 scored test hours is about -0.04 points overall; say this in the report so nobody over-reads a PASS. The 0.25 FAIL line is reasonable. The 2% by cell is fine with F10. The 300-hour floor is not binding (all four cells exceed it). The 15% lines are well chosen (they match the advisory latch and A6's S1). The 0.5 pp allowance on readings 15% or more too high is fair.

**13. Dead ends and missed lessons.** It is not the floor gate in reverse: it changes no cell. But it carries two of that study's lessons. (a) Near-threshold hours are the noisiest (floor gate: 54% of flips got worse). The replay uses hourly medians; production's 15-minute readings make `d6` near the threshold noisier, so the replay likely overstates how well `d6` separates gentle from steep rises. Say so in section 11. (b) "Static leverage is not prequential gain": A1 is static; the plan correctly decides on B. It does not repeat C45 phase 2 (≥25,000 cfs untouched). It respects A6 and A7's lesson to judge the shown value, and it should also respect their second lesson, the unsafe direction (F3). Missed lessons: the span of the state rule is a lever (v35.0; F4); A7's "new data" rule (F5); the EMA's short memory (F2).

**14. The strongest argument against running it.** The best plausible outcome is small and hard to carry to production. Even a full PASS (-0.50 points on affected hours) moves the headline error by about 0.04 points. The replay's state span (4 h), resolution (hourly medians) and the browser's own state rule (robust endpoints, NWS fallback) all differ from what a visitor's screen uses, so m* and its gain would not transfer as measured. The gap between rising and steady values is to a large part recency noise of an EMA with alpha 0.3, which a state-blend rule cannot target on purpose. The author's own estimate is a one in two chance of FAIL or UNCLEAR, and even a PASS leads only to another plan, a MAJOR release in two code paths, and (by F5) a prospective check. Against that: the study is cheap (one replay, offline arithmetic), application-only, needs no reset, and would close D20 cleanly either way. On balance it is worth running if F1 to F5 are fixed, mainly because a clean FAIL also has value.
