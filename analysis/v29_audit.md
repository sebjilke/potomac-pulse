function getEFWeight(estimatedFlow) {

### E11. Flat 35% Step Function Regression Risk -- MODERATE (acceptable)

The Python and R reports both show the flow-regime tradeoffs:

| Regime | Direction | Magnitude |
|--------|-----------|-----------|
| <3k cfs | No change | 0% (both use 0 weight) |
| 3-6k cfs | **Improved** | -11% RMSE |
| 6-10k cfs | **Improved** | -5.6% to -8% RMSE |
| 10-15k cfs | **Degraded** | +2% to +4% RMSE |
| 15-25k cfs | **Degraded** | +4% to +5.1% RMSE |
| 25-50k cfs | **Degraded** | +4.2% RMSE |
| >50k cfs | **Improved** | -10% RMSE |

**Concern:** The flat 35% weight is slightly worse at 10-50k cfs (the old gradient used 40% in this range). For users specifically interested in rising-river/high-water events (which is arguably the primary use case for a Great Falls estimation tool), 10-50k cfs is the most operationally relevant range. The degradation is modest (2-5%) and the overall RMSE improvement is genuine, but this tradeoff should be clearly communicated.

**Mitigating factors:**
- The 3-10k cfs range has 3x more observations than 10-50k, driving the overall improvement
- Cross-validation shows the result generalizes (4/6 years improve)
- The absolute RMSE increase in 10-50k is small (30-155 cfs depending on bin)
- The simplicity of the flat step reduces overfitting risk

**Verdict:** Acceptable. The tradeoff is well-documented in the Tech Appendix and is a reasonable engineering decision.

### E12. CLAUDE.md Concerns -- MINOR ISSUES

**Issue 1 -- RMSE numbers inconsistency:**
CLAUDE.md line 113 states:
> RMSE: 1,676 cfs (flat 35%) vs 1,702 (old graduated) vs 1,757 (daily-optimized) = -4.6% improvement.

But the Python and R verification reports both computed:
- NEW (flat 35%): **1,679.1 cfs** (not 1,676)
- OLD (daily graduated): **1,756.8 cfs** (not 1,757)
- Improvement: **4.4%** (not 4.6%)

The 1,676 figure appears to come from the optimization script, while 1,679.1 comes from the independent verification backtest. The 3 cfs difference is trivial, but using the optimization script's own output rather than the independent verification's output is a **best-practice concern** -- the verification number should be canonical.

Similarly, the -4.6% improvement is computed from the rounded numbers: (1757-1676)/1757 = 4.61%. The actual verified improvement is (1756.8-1679.1)/1756.8 = 4.42%. This is a minor rounding artifact but could be more precisely stated.

**Issue 2 -- "1,702 (old graduated)" is confusing:**
The CLAUDE.md line compares three numbers: 1,676 vs 1,702 vs 1,757. The "1,702" is the v1 hourly optimization (flat 40%), not the "old graduated" v27.0 weights. The parenthetical "(old graduated)" is applied to 1,702 but the actual old graduated ramp (v27.0) produced 1,757. This labeling is misleading.

From the Tech Appendix line 5622-5624:
- Flat 35% (v29.0): 1,676
- Flat 40% (v1 hourly): 1,702
- Graduated 0->10->40% (v27.0 daily): 1,757

The CLAUDE.md should label these consistently with the Tech Appendix.
