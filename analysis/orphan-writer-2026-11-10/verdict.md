# A10 verdict: who writes rise_event rows (checked 2026-11-10 ~17:58 UTC)

## Bottom line
Writer = Supabase edge function `potomac-learner` (v1, deployed 2026-01-14, not in the repo), fired every 15 minutes by pg_cron job 2 `potomac-learning-job` (`*/15 * * * *`, active=true) via pg_net. It never stopped. It is still running today and still TRYING to insert rise_event rows; inserts fail on the unique key and the function ignores the error. Confidence: established.

## Re-checked myself (read-only)
1. cron.job: only job 2 exists, schedule */15, active=true, command = net.http_post to .../functions/v1/potomac-learner with an Authorization bearer header. The embedded JWT decodes to role=anon (key not reproduced here). NB investigator 1 said the function uses the service-role key: true inside the function (reads SUPABASE_SERVICE_ROLE_KEY env); the cron caller uses the anon key.
2. cron.job_run_details: job 2 = 28,791 succeeded runs, 2026-01-14 20:15 to 2026-11-10 17:45 UTC. DB now() at check = 17:57:45, so the 17:45 run is the latest due run. Job 1 failed once 2026-01-14 20:00 (no longer in cron.job). Caveat: "succeeded" only means pg_net queued the request.
3. net._http_response (retention ~6h): 24 x HTTP 200, 12:00 to 17:45 UTC today. Latest body: {"success":true,"rises":1,...17:45:01Z}. So today the function detected a rise and called insert; the row count is still 9, so the insert did not land (fails on unique key, error not checked in code).
4. Function source (get_edge_function): plain `insert` of rise_event when (current.q - prev.q)/prev.q >= 0.02 against the `snapshot/current` row; then `upsert` snapshot and metadata with no onConflict. Errors from insert/upsert are never inspected, so the function returns 200 regardless.
5. rise_event rows: exactly 9, created 2026-06-18 20:30:00.90 to 2026-07-10 00:45:00.93; data.timestamp precedes created_at by 0.04 to 0.14 s each. Newest inner timestamp 2026-07-10T00:45:00.792Z. Gauges 01643000, 01644000, 01645000, 01611500, 01638500, 01610000, 01636500, 01613000, 01618000. The function's other two non-LF gauges (01636000 Harpers Ferry, 01620000 Cumberland) have no row (reason not checked; likely never crossed 2% vs the January baseline or no prev q).
6. snapshot/current created 2026-01-14 20:05:17 (never updated, so the 2% comparison is against a January baseline, which is why "rises" fire on ordinary flows). metadata/system created 2026-06-18 20:30:00.96, same run as the first two rise rows.
7. git: v37.1 = 8062113, 2026-06-18 16:12:32 -04:00 (20:12 UTC). Its plan deleted rise_event (expected 9) plus the 'metadata'/'system' row, believing both were System-1 client artifacts with "zero source refs". Refill began at the next quarter hour, 20:30 UTC. `git log -S rise_event --all` shows only 8062113 and two docs commits; no writer code ever in repo.
8. HEAD app code does not read 'snapshot' or 'metadata' rows (only gf_metadata / gf_forecast_metadata). So the stale rows feed nothing in the app.

## Reconciling investigators
- Database and hosting angles agree and are confirmed. Local angle ("unknown") is superseded: the writer is off-Mac, inside the same Supabase project.
- Audit REPORT framing "something outside this codebase" is right; "may still be attempting writes every 15 minutes" is confirmed, not hypothetical. It is not an external third party; it is the project's own Supabase.
- v37.1 plan misattributed rise_event and metadata/system to System-1; they belong to this edge function. Pre-deletion the table also held exactly 9 rise_event rows, i.e. the function had saturated the same way before and simply refilled after the delete.

Not fully excluded for the June/July rows because logs older than 24h are gone, but no evidence for it and pg_cron fully explains every row.

## Recommended action (owner decision; nothing changed)
1. Unschedule pg_cron job 2: `select cron.unschedule('potomac-learning-job');` This stops all writes. Verify: cron.job empty for it; no new net._http_response rows after the next quarter hour.
2. Then delete edge function potomac-learner (dashboard or CLI); it is reachable by anyone holding the public anon key since verify_jwt only requires a valid JWT.
3. Only after 1 and 2: owner may delete the 9 rise_event rows, metadata/system, and snapshot/current (all owned by this function, none read by the app). Do the cleanup after stopping the writer, or the rows refill at the next quarter hour (exactly what happened after v37.1).
4. Correct the v37.1 plan/CHANGELOG note that rise_event was a legacy artifact with zero source refs.
Optional hardening (separate decision): RLS "Allow public access" ALL for public role lets anyone with the anon key write any row.
