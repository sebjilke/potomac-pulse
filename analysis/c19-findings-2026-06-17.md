# C19 — client/server ensemble parity: closure + a new flow-state finding

**Date:** 2026-06-17
**Author:** implementation session (Claude Opus 4.8)
**Relates to:** C19 (science-review-2026-06-10.md:68), and the flow-state-classification

## 1. C19 is closed

The science review's C19 ("No test enforces client/server parity; the characterization
suite *computes* divergence but never asserts it") is addressed by
**`test/ensemble-parity.test.mjs`** (added this session; full suite 391 → 407 green).

The new test goes beyond the characterization snapshot, which only asserts client↔server
equality on `cfs` and `flowBin`. It is structured in two tiers:

- **Tier 1 — strict parity on dense clean history.** Across a 4-flow-level × 3-flow-state
  grid (+ cold-water + populated-correction-bin cases) it asserts client (`estimateGreatFalls`)
  and server (`makeGFPrediction`) agree on **every** comparable ensemble field:
  `flowState, flowBin, porEstimateCFS, historicPorCFS, useTimeShifted, useEfEnsemble,
  efWeight, correction, ceilingApplied, finalCFS`. This locks the two duplicated ensemble
  implementations in lock-step and confirms the v36.0 shared end-apply correction carries
  through the whole pipeline (`rawFinalCFS − predictedCFS == correctionApplied`).
- **Tier 2 — characterized divergence (see §2).** Pins the one place the two *intentionally*
  disagree, so it cannot change silently.

Note: the named `glitch-history` characterization fixture does **not** actually produce a
client/server divergence — the 1.5h-old spike never enters the ~6–19h historic-PoR lookup
window, and both sides return `historicPorCFS = null` and classify identically. The real
residual is flow-state classification under coarse sampling (§2), not glitch handling.

## 2. New finding — flow-state classifiers diverge on hourly-cadence history

**Mechanism (verified in the harness, deterministic):**

| | Client `getPoRRiseRate` → `robustCurrentReading` | Server `getFlowState` |
|---|---|---|
| File | `src/estimation/rise-rate-robust.mjs:40-47` | `netlify/functions/shared/model.js:114-126` |
| Gate to classify a trend | ≥3 readings inside a trailing **90-minute** window | ≥8 history entries **and** a reading ≤6h old |
| On **hourly** history during a steep rise | only 2 points fit the 90-min window → returns `null` → flow state falls back to **`steady`** | still finds a ≤6h reading, change > threshold → **`rising`** |

Same input, different answer. Confirmed empirically: a +6%/h rise at PoR≈22k classifies
`rising` on both sides at 10-min cadence (parity), but `steady` (client) vs `rising` (server)
at 60-min cadence. This is the dominant "C19 ensemble residual" — and it is **cadence-driven,
not glitch-driven**.

**Why it could matter (v36.0 "displayed == validated"):** the browser **display** path
classifies flow state from the *client's localStorage* PoR history; the **cron** path
(learning + the v36.0 displayed==validated basis) classifies from *freshly-fetched* history.
If the client's stored history is ever hourly-or-coarser **during a real rising/falling limb**,
the displayed estimate looks up the `steady` correction bin while the server learns/validates
`rising` — so displayed ≠ validated, and the client under-applies the flow-state correction on
exactly the dynamic events that matter most.

**Calibration — verified 2026-06-17 (severity downgraded).** The client's PoR history is a merge
of two feeds:

- **Local poll points at ~15-min cadence** — `setInterval(fetchData, 900000)` (`src/main.js:53`),
  `recordPoRReading` deduped to one slot per 10 min (`src/data/history.js:112-134`). Present only
  while the tab is open and actively polling.
- **Hourly server-feed points** — `fetchServerPoRHistory` merges the cron-written `por-history`
  endpoint (`src/data/history.js:44-98`); the code itself notes *"local-only points between hourly
  cron samples"* (history.js:70), i.e. the server feed is **hourly**. This is the **only** source
  on a fresh page load.

Therefore:

- **Steady-state (tab open ≥~90 min):** the local 15-min points densify the trailing 90-min
  window (≈6 points ≥ the ≥3 gate) → the client classifies the trend → **parity holds, the
  divergence does NOT bite.** The v36.0 displayed==validated guarantee is intact in normal use.
- **Cold start / backgrounded (stalled-poll) tab:** the trailing window is populated only by the
  hourly server feed → ≤2 points in 90 min → client robust classifier returns null → flow state
  comes from the **NWS-trend fallback** (`great-falls.js:461`), not the PoR-based classifier the
  server uses. This is a real client/server divergence, but bounded to the cold-start / inactive
  window — exactly the scenario already tracked as **C41 (cold-start flow-state differs)**.

So this is **not a new steady-state bug**: it is the precise *mechanism* behind the existing C41,
and it is confined to the first ~90 min after a fresh load (or after a long poll gap). Remaining
sub-question (defer to the redesign): at cold start the client lands on the NWS-trend fallback
rather than necessarily `steady`, so the production divergence direction depends on NWS
availability — worth pinning when C41/#7 is taken up.

**Relation to existing findings:** this is the window-density mechanism (client robust current
reading needs ≥3 pts / 90 min) underlying **C41 (cold-start flow-state)**. Distinct from C10
(server min-history 8 vs a client min of 4 — a different gate).

## 3. Disposition

Deferred into the **flow-state learning-gate redesign** backlog item (parcel-aligned). That
redesign is the right place to decide whether client and server should share one flow-state
