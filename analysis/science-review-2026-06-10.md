# PotomacPulse — Salvaged & Re-Verified Scientific Review

## Provenance

This is a **salvaged review.** The original multi-agent assessment was run on **2026-06-10** by model **claude-fable-5** and was truncated by a session limit before it could verify or synthesize its own raw findings. Those raw findings were recovered, deduplicated into 53 distinct claims (C1–C53), and **each claim was then independently re-verified on a fresh model by two adversarial verifiers** whose only job was to refute it against the live code, the live Supabase database, and fresh USGS/NWS data.

The verification status reported here is the **aggregate of those two verifiers**, and it is reported honestly:

- **confirmed** — both verifiers reproduced the claim against ground truth.
- **downgraded** — the mechanism is real but at least one verifier found the severity overstated, or found a mitigating fact the original review missed; the claim is true but smaller than first stated.
- **refuted** — verifiers found the claim's load-bearing assertions contradicted by the code, data, or the project's own backtests.
- **uncertain / disputed** — verifiers disagreed or could not settle it. (No claim landed in these buckets after aggregation; two had split per-verifier verdicts that resolved to confirmed/downgraded, noted inline.)

**uncertain is not confirmed; downgraded is not refuted; refuted means the claim is wrong, not merely unproven.** Where the two verifiers disagreed on severity, I report both sides in one line and take the more conservative reading.

One process limitation up front: the synthesis brief pointed at a `lens_assessments` artifact for the per-lens letter-grade narrative, but **that path resolved to `undefined` and no project file contains the field.** The letter grades below are therefore *my* synthesis from the re-verified claim set and the project's own analysis corpus, not a recovered artifact. Treat them as the reviewer's judgment, not a salvaged score.

## Executive summary

PotomacPulse is, for a solo-built whitewater tool, a genuinely serious piece of hydrological engineering. It routes a real upstream→downstream advection model (Point of Rocks → Great Falls, flow-dependent travel time), blends in an independent Edwards Ferry stage-discharge estimate with a calibrated logistic weight, quantifies uncertainty with empirical per-bin quantiles rather than a hand-waved Gaussian, and runs an online learning loop that validates past predictions against the downstream Little Falls gauge. The analysis corpus behind it (horse races, dual-language Python/R verification, backtests over 42k–117k hourly observations) is more rigorous than most published operational nowcast tools. The **methodology is largely sound; the problems are overwhelmingly in the gap between what the documentation claims and what the deployed code actually does.**

That gap is the headline finding. The single most consequential confirmed result is that **the model the system validates, stores, graphs, and reports accuracy for is not the model users see.** The server never applies the learned EMA correction; the browser does. So the headline "~6.6% / ~6%" accuracy describes the *uncorrected* model, while the displayed estimate is corrected and never scored anywhere (C1, C37). Layered on top are an asymmetric-CI that ships symmetrized (C2), a forecast-vs-NWS baseline comparison that has *never* run because the database insert silently drops the baseline fields (C24), a five-month-silent data-sync failure that reports itself healthy (C46), and an unauthenticated write path that can poison the correction bins shown to every user (C13).

None of the confirmed defects make the tool dangerous in the ordinary sense — at the steady low-to-moderate flows paddlers care about, the displayed number is plausible and the 120% ceiling keeps it tethered to a real downstream gauge. The defects instead mean the **scientific claims the tool makes about itself are not currently true as written**, and several of its most sophisticated-sounding features (asymmetric uncertainty, NWS skill comparison, EF forecast ensemble, adaptive hysteresis) are inert or mis-wired.

### The 5–7 most consequential confirmed findings

These lead because they are confirmed and, where flagged, **converged independently across many of the original review's lenses** (`source_lens_count`), which strengthens them.

1. **The validated model ≠ the displayed model (C1, confirmed, 7 lenses).** Server `makeGFPrediction()` never imports or calls the bin correction; the client subtracts it. Every stored prediction, graph line, validation error, and the headline accuracy number describe the raw model; users see the corrected one (~13% / up to 700–1,400 cfs apart). The displayed estimate is never scored.
2. **Headline "~6% nowcast error" is not the production number (C37, confirmed).** The project's own hourly backtest at the exact production config (decay 0.50 / ceiling 120%) reports **~11% MAPE** (n=42,837); ~6% is the daily-averaged figure. The app runs and validates hourly.
3. **Forecast skill vs NWS has never been measurable (C24, confirmed, 3 lenses).** The client computes and POSTs the three NWS/persistence baselines, but the `sync-learning` insert whitelists six fields and drops all three. Production confirms: 0 of 158 pending forecast rows carry baselines; `nwsRawValidations` is NULL after ~1,800 validations each. The feature's central scientific question is unanswerable.
4. **The displayed 90% CI throws away the asymmetry it was built to capture (C2, confirmed, 5 lenses).** The appendix and the project's own error-distribution audit specify an asymmetric `[est+q05, est+q95]` band precisely because errors are severely non-normal (ratios to 42:1); the code ships `est ± (q95−q05)/2` — a symmetric band. The documented formula is itself sign-flipped.
5. **Estimand mismatch (C32, confirmed, 3 lenses).** Every calibrated component targets Little Falls discharge (validated against raw `lf.q`, EF fit to LF, CI of predicted−LF, cap at 1.2×LF). The "Great Falls flow" the app displays is structurally "LF discharge ~6.5h ahead," and the appendix's claim that validation "calculates what GF actually was" is false as written. USGS adjusted-flow data put the GF-vs-LF wedge at a median 32% of LF on low-flow days.
6. **A five-month silent data failure that self-reports as healthy (C46, confirmed).** System-1 gauge-observation sync inserts into a table with `UNIQUE(observation_type, gauge_id)`; the second insert per gauge always violates it. Production has exactly 18 observation rows, all written in one second on 2026-01-14, none since — yet the endpoint returns 200 and the UI shows "synced."
7. **Unauthenticated write path can poison every user's estimate (C13, confirmed, 2 lenses).** `sync-learning` validates only top-level body fields; the actual numbers are nested under `body.prediction`/`body.forecasts[]` and inserted unchecked, with no auth (PIN only gates resets). A crafted prediction enters the EMA and is subtracted from the estimate shown to all users.

## Scientific credibility — nowcast

**Routing and travel time.** The core advection idea is correct and the implementation is internally consistent across runtimes for the *formula*: `T = 4139·Q^−0.5963` (Q floored at 1,000 cfs) appears identically in `constants.js:117-122` and `netlify/functions/shared/model.js:104-108`, and is pinned by tests. The scientific problem is twofold and both verifiers confirmed it. First (C6, confirmed), the *documentation* of this formula is wrong at low flow: the §3.3 table and the "19–33h PoR→GF" range repeated across CLAUDE.md:101, README, the appendix, and index.html:389-393 do not match the formula below ~2,000 cfs. The true PoR→GF operating range is ~5h (50k cfs) to ~50.6h (1,000-cfs clamp); 19.4h is the *median-flow* value, not the high-water value index.html labels it. A reader sanity-checking the model against the appendix would conclude the code is broken when it is the table that is stale. The completeness critic independently spot-checked this and found the divergence *understated* — the doc's 33h ceiling is only reached at ~2,000 cfs and the formula blows past it below that.

Second, and more fundamentally (C23, downgraded to minor): the deployed relation is empirically a **kinematic wave-celerity (signal) time, mislabeled in the docs as dye-tracer water travel with a "changed channel conditions" rationale.** Fresh USGS 15-min data (Oct 2025–Jun 2026) show the formula overestimates the observed hydrograph lag by 10–16h (35–71%) for LF 1,400–4,000 cfs, while matching within ~1h above ~17,000 cfs. The verifiers downgraded severity (the *direction* of the bias is documented as a known limitation, and the appendix even contains a better-fitting modern relation `T = 2438·Q^−0.5491`, R²=0.908, that was set aside to "preserve Searcy's exponent"), but the underlying science critique stands: a discharge hydrograph should be time-shifted by wave celerity, which is faster than water velocity, and the rising-only celerity add-on is too small and partially double-counts. **This is the single most defensible "improve the actual estimate" opportunity, and it maps directly onto TODO Tier 0.**

A related parity defect (C8, confirmed): only the *client* runs the documented §3.5 iterative convergence (3 iterations, 1h tolerance); the *server* — which generates every stored/validated prediction — computes the multiplier once from current LF and does a single lookup. So the authoritative prediction uses a systematically different time-shift than the browser on rising/falling limbs. C16 (downgraded) compounds this: the server keeps only 48h of PoR history (and fetches only `P2D`), which is shorter than the low-flow PoR→GF travel time (~50.6h at the clamp), so in deep drought the server silently falls back to *un-shifted* current PoR with no flag, while the client keeps 72h. Client and server diverge precisely when flows are most sensitive.

**Edwards Ferry relation.** The EF stage-discharge power law is a genuine strength in concept — a second, independent observable that the system fuses with the upstream route via a calibrated logistic weight. But fresh data are unkind to the deployed coefficients (C42, confirmed). On Oct 2025–Jun 2026 hourly data the default warm power law `126·EF^2.46` is biased low by ~10–12% (median signed) for LF 3,000–12,000 cfs, and — strikingly — the *cold* coefficients `160·EF^2.36` fit the *warm* subset better than the warm coefficients do (median |err| 6.0% vs 9.3%), which undercuts the stated temperature-switch rationale. (One verifier confirmed at major; the other reproduced the same fetch and downgraded, finding the magnitude sensitive to the exact temperature/range filter — so treat the ~10% as a real, directionally-robust bias whose precise size depends on windowing.) The temperature switch itself (C52, confirmed) steps discontinuously at exactly 10°C with no hysteresis, and its physical justification ("higher density and viscosity") is weak — at Potomac Reynolds numbers viscosity is near-irrelevant; the effect is almost certainly seasonal confounding (vegetation/SAV rating shifts, residual ice). The *empirical* split is defensible (it improved winter RMSE); only the causal story is wrong.

The EF accuracy metadata is also a mess across the project's own sources (C9, confirmed, 4 lenses): the appendix reports R²=0.94 — a value the project's *own* verification report explicitly debunked as a duplicated-data artifact — while everything else says 0.91; the obs count is the duplicated 10,434 in one place and the deduplicated 5,220 elsewhere; the advertised "6.3% median error" is daily-resolution while the hourly refit measured 11.7%. And the documented blend (C11, downgraded; C5, confirmed) has provenance issues: the logistic weight was calibrated on *actual* LF discharge but production feeds it the *PoR estimate* (corrected on client, uncorrected on server), and the §5.4 illustrative table doesn't match the deployed K=5 curve (off by up to 18× at 3,000 cfs).

**Mass balance and withdrawals.** This is where the science is most honest in intent and most muddled in artifact. The decision to validate against raw Little Falls discharge is *defensible* — paddlers read Great Falls conditions off the LF gauge, and the project documents the trade-off. But the estimand mismatch (C32, confirmed, 3 lenses) is real and unacknowledged in the user-facing claim: the output is "LF discharge ~6.5h ahead" relabeled as Great Falls, the GF-vs-LF wedge (below-falls Aqueduct withdrawal minus intervening tributary inflow) cannot be learned because no GF observation ever enters the error signal, and the signed error inseparably bundles water balance, tributary error, travel-time error, EF rating error, and model bias inside each bin. USGS adjusted-flow (01646502) shows diversions median 32% (max 65%) of LF on low-flow days, so at summer low flow the displayed number understates physical GF discharge by ~10–30%. The appendix's §6.1 claim that validation "calculate[s] what GF actually was" is **false as written.** The governing v34.0 audit that approved this also states a geographically wrong mass balance (C33, downgraded) — it places the entire 400–700 cfs metro withdrawal *below* the falls, when most intakes (WSSC at Swain's Lock, Fairfax/Corbalis near Seneca, the Aqueduct's Great Falls dam) are *above* — but verifiers downgraded it because the error lives in internal reasoning with no output impact and the user-facing appendix has the geography right.

**Learning statistics.** The binned signed-error EMA is a reasonable serial-bias feedback *while the river stays in one bin/state*, and the hierarchical shrinkage fallback (C44, confirmed minor) is a sensible cold-start guard. But the statistical premises are shaky. The realized validation cadence is ~3.5–4/day, not the "12/day" the design assumed, because only one prediction can be pending at a time (C43, downgraded; C7, confirmed). Errors are heavily autocorrelated, so an α=0.3 EMA carries roughly single-observation noise; live data show only ~6 of 18 bins reach count≥10 and 5 bins are empty, so most "corrections" are 1–2 effective observations and there is no calendar-time decay for stale bins. Verifiers downgraded the severity (the autocorrelation makes the EMA *useful* as bias feedback while the regime holds; it is unambiguously harmful only at transitions and in sparse bins, and one audit doc the original review missed does discuss α) but confirmed every structural fact. The ±2σ clamp documented as protecting against single large errors is largely inert (C15, downgraded): the clamp only fires at softScore≥2 *and* count≥10, a large error alone scores only +1, and the clamp computes σ from sums that already include the outlier it is trying to clamp. The applied correction is also a **step function** of bin and state (C45, confirmed) with no interpolation or hysteresis, producing ~24% / ~1,400 cfs display jumps as flow crosses 6,000 cfs and rising-to-steady flaps near the threshold — and the adjacent sign reversals between sparse bins (−1,424 vs +401) confirm these are event noise, not regime bias.

**Uncertainty / CI.** The intent — empirical per-bin asymmetric quantiles instead of a Gaussian — is exactly right for these severely non-normal errors, and the project documents *why*. The implementation throws it away (C2, confirmed, 5 lenses): it ships `est ± (q95−q05)/2`, a symmetric band re-centered on the estimate, discarding the asymmetry the method exists to capture, and the documented formula is itself sign-flipped relative to a correct predictive band for actual flow. For a safety tool this systematically understates upside risk on rising water.

**Genuine nowcast strengths** worth stating plainly: the multi-gauge advection + EF fusion is a real model, not a lookup; the analysis discipline (dual-language Python/R agreement, independent auditors, horse races, 42k–117k-obs backtests) exceeds most operational tools; the soft cap is empirically grounded (C34 refuted the "no basis" charge); and the system correctly excludes hard-flagged corrupt data from learning.

## Scientific credibility — forecast

The forecast is architecturally distinct from the nowcast — it anchors on NWS Little Falls forecasts and shifts them by GF→LF travel time rather than pushing upstream readings forward — which is a sound choice. But it is the weaker half, and its weakest property is that **its central scientific claim is currently unfalsifiable.**

The advertised feature is that the 48h forecast is "scored against two NWS baselines (raw and bias-corrected) at each horizon." This has **never operated** (C24, confirmed, 3 lenses): the client computes and POSTs `nwsLfRawCFS`, `nwsLfBiasCorrectedCFS`, and `persistenceCFS`, but the `sync-learning` insert rebuilds the row with a six-field whitelist and drops all three. The validator's baseline blocks are guarded by `if (pred.data.nwsLfRawCFS)` and can never fire; the "vs NWS LF forecast" UI row needs `nwsRawValidations≥10` and can never render. Production confirms it end-to-end: 0 of 158 pending rows carry baselines, `nwsRawValidations` NULL after ~1,800 validations. So the question the feature exists to answer — *does the model beat raw NWS?* — has no answer, and the published per-horizon MAPE (10.9/10.4/11.5/18.8% at +6/12/24/48h) stands alone with nothing to compare against.

Even the standalone accuracy numbers carry a structural bias (C25, downgraded but 5 lenses): a +Nh forecast is *constructed* as the NWS LF forecast for t+travel (a statement about LF ~6.5h later), but it is *validated* against LF at cron time with no GF→LF offset and no upper delay cap — while the nowcast validator *does* wait for water arrival. The system is internally inconsistent about what its own GF numbers mean, and the model-vs-baseline comparison embeds a ~6.5h phase mismatch that inflates apparent error on limbs. Verifiers downgraded (the bias direction is mixed and partly self-canceling) but confirmed the mechanism and the documentation mismatch with the "validated when water arrives at Little Falls" claim.

Two documented forecast features are effectively dead. The EF forecast ensemble (C26, downgraded) is unreachable three independent ways (EF's USGS id absent from `NWS_LIDS`, absent from the client `GAUGES` table, and the live EF NWPS forecast is stage-only so the flow parser would discard it); production shows 0 forecasts ever labeled "NWS+EF." The PoR fallback (C22, confirmed) returns the PoR NWS value at the GF target time with **no PoR→GF travel offset and no tributary scaling**, understating GF by ~12–17% and misplacing features by up to a day, all under the same "NWS" label — and the function written for exactly this offset (`getTravelTimeAwarePor`) is never called. The NWS branch gate is also inverted (`hasNWSForecast = hasPoRForecast`), so a usable LF forecast with a missing PoR forecast falls through to linear extrapolation.

Smaller but real: the additive bias offset is held flat to +48h with no lead-time decay and is often anchored to a forecast point hours in the future (C27, confirmed); the GF→LF offset is frozen at current flow for all 48 hours (C31, confirmed); the linear-extrapolation fallback — the weakest mode — is styled identically to NWS and carries a tooltip that *calls* it an NWS forecast (C29, confirmed); the UI hardcodes the kcfs→cfs ×1000 conversion without a unit check and is exposed to the NWS −999 sentinel (C30, confirmed); and the entire forecast sample is browser-traffic-driven and pseudo-replicated (C28, confirmed) — up to 6 duplicate +6h forecasts in one hour, none overnight — so the ~1,800-per-horizon "sample" overweights high-traffic periods and inflates apparent n. Finally, EMA corrections apply only to the nowcast, so the +6h trend arrow can show a ▲/▼ that reflects the method switch at t=0, not a predicted change (C53, confirmed).

**Forecast strengths:** the additive-vs-multiplicative bias choice is defensibly documented, extrapolated forecasts *are* correctly excluded from accuracy tracking, and the 0.3 damping floor is conservative. The skeleton is sound; the wiring is broken.

## Implementation quality

**Client/server parity.** This is the structural theme behind a third of the findings. The system maintains three runtimes (browser `src/`, server `netlify/functions/`, and the `index.html` legacy shell — though index.html is now a 678-line thin loader, C10), and they have silently drifted. The EMA correction is client-only (C1); EF hysteresis is client-only and frozen (C4); travel-time iteration is client-only (C8); the ice qualifier parse differs (C3); cold-start flow-state differs (C41); the flow-state minimum-history threshold is 8 server vs 4 client (C10). Critically, **no test asserts parity** (C19, confirmed): the characterization harness *computes* per-fixture divergence and writes it to a report, but the assertions only check each side against its own snapshot — and that report has already captured a genuine bin-keying bug (client keys corrections on the pre-blend estimate, server on the final post-blend/ceiling prediction) on two fixtures, with no failing test and no tracking disposition.

**Data layer.** The ingestion layer is where bad data enters and it is both untested and inconsistent. The server ice detection is dead code (C3) because it parses USGS string qualifiers as objects (verified against the live API), so an ice-corrupted-but-numeric LF reading passes as clean and enters the bins in winter. Neither side checks reading age (C17), and the server takes only the single latest value with no walk-back, so one bad reading skips a whole cycle. `fillMissingData` copies Point of Rocks' stage to unrelated gauges (C49), displaying a physically meaningless datum-referenced number. The ~3 MB raw-JSON localStorage cache sits near the quota and may silently never populate on Safari/iOS (C48). And both estimate and validation target are pinned to provisional values that get revised away within minutes (C50).

**Reliability.** Two defects share the failure class of the recorded 270-hour v34.19 outage. The validation pipeline is **non-idempotent** (C12, confirmed): the correction-bin, stage-bin, and EF-correlation upserts all commit *before* the pending row is deleted, and the delete is log-and-continue — so a mid-run death (Netlify 30s limit; up to ~300 sequential Supabase round trips under forecast backlog) double-counts the observation. Worse, a single malformed `validationDue` **permanently deadlocks** the pipeline: the `isNaN` guard sits before the 48h cleanup so the bad row is never deleted, and `storePrediction` then computes `pastWindow=false` forever, skipping all future predictions. That bad row is injectable via the unauthenticated POST. The EF-correlation `sumCFSSq` double-counts the newest point each cycle (C14, confirmed in live data: stored value exactly 5220² high). All shared state is single-row read-modify-write with no concurrency control (C47), and `gf_metadata` is read-and-upserted at three points per run.

**Security.** The write path is unauthenticated and under-validated (C13, confirmed). `sync-learning` validates only top-level fields; the actual prediction/forecast numbers are nested and inserted unchecked with service-role privileges (RLS confirmed enabled but bypassed by the service key). The PIN gates only resets; CORS doesn't stop non-browser clients; the rate limit is in-memory per-instance. A crafted `predictedCFS=1e8` with a near-term `validationDue` enters a free pending slot, is "validated," and its error enters the EMA — the >50% anomaly check is only a soft +1 and the z-score guard needs ≥10 prior obs (several live bins have 1–3). This connects directly to the user's own backlog item about the service-role key in plaintext settings (TODO Tier 1 #3) and the RLS item (Tier 1 #1).

**Tests / CI.** The characterization suite is a real asset and the team clearly values testing. But the coverage map has holes exactly where risk concentrates (C18, confirmed): the entire learning/validation core, all of `sync-learning` (870 lines, no test seam), both halves of the forecast pipeline, the client model copy, and both ingestion layers are untested; the 8 fixtures never exercise the ceiling, ice, missing-gauge, hysteresis, sparse-bin, or flow-extreme cases. Test-infra defects (C21, confirmed) include an undeclared `esbuild` dependency (resolves only via vite hoisting), a repo-writing test, and a baseline test that silently re-baselines on a missing snapshot. And the capstone (C20, confirmed): **CI is advisory — Netlify deploys via `npm install && npm run build` (just `vite build`), which never runs tests.** A commit that breaks the suite still ships to production.

## Review limitations

This synthesis rests on the re-verified claim set plus one independent spot-check; it is not a fresh from-scratch audit, and the following areas were under- or un-examined.

- **Rating-curve / shifting-control drift over time was never examined.** The EF power law and the LF "actual" target both rest on USGS stage-discharge ratings that USGS revises after high-water and channel/sediment shifts; a coefficient fit on old ratings silently biases both the estimator and the ground truth. No claim touches whether the calibration vintage still matches current ratings.
- **Upstream dam/reservoir regulation (Savage, Jennings Randolph, Little Seneca/WSSC) is absent.** The routing assumes free advection; regulated releases and water-supply withdrawals break the PoR→GF mass balance non-stationarily — directly relevant to the untested claim that the EMA "absorbs withdrawals."
- **Datum/units and provisional-vs-approved revision are only half-covered.** One claim notes provisional revision (C50), but nobody checked NAVD88 vs gauge-datum consistency, or that the kcfs↔cfs ×1000 site (C30) is the *only* unit-mismatch site. A second occurrence would invalidate the nowcast too.
- **No dependency / supply-chain or secret-exposure review.** `package-lock` pins are unaudited, and the user's own memory flags a service-role key in plaintext settings — a write-path poisoning vector adjacent to C13, never connected to it here.
- **Monitoring/alerting blind spot is asserted, not its absence-of-detection proven.** The review says System-1 failed silently ~5 months (C46) and run-health "reports itself healthy" (C7), but no claim audits what *would* page a human, or whether any alert path exists. That is the meta-failure behind half the major findings.
- **Backwater / hydraulic control at Little Falls itself is unexamined.** LF discharge under high Potomac stage or tidal/backwater influence can decouple from the rating — and LF is simultaneously the validation target and the soft-cap anchor.
- **Low-flow vs flood-regime asymmetry is under-tested.** The verified spot-check found the deployed formula gives PoR→GF = 33.5h at ~2,000 cfs and 50.6h at ~1,000 cfs, far outside the documented "19–33h" — so C6/C23 are real *and understated* — but no claim quantifies how often drought flow actually occurs, leaving severity unscored.
- **Internal contradiction left unreconciled:** claims simultaneously assert the server "never applies EMA correction" to the stored/graphed model (C1) *and* that EMA corrections "contaminate the forecast trend arrows" / poison "bins shown to every user" (C13, C53). Whether the correction is inert or harmful changes the priority ranking; the review never fully resolves which (the resolution: it is inert *server-side* but live *client-side*, and harmful *if poisoned* — but this should be stated, not inferred).
- **Effective-sample-size claims (~1–2 obs, "near single-observation variance," C43) are accepted without a primary autocorrelation estimate** from the actual validation series — they are plausibility arguments, not a measured ACF on PotomacPulse's own data.
- **Data retention / cost / durability** is touched once (3 MB cache, C48); no review of Supabase row growth, unbounded validation-table accumulation, or function timeout under large histories.
- **Process limitation:** the promised `lens_assessments` artifact path resolved to `undefined` and no project file contains that field, so the per-lens reasoning/evidence could not be cross-checked and the **letter grades above are the reviewer's synthesis from the claim set, not a recovered score.** The original review's model (claude-fable-5) never completed its own synthesis, so the lens narratives are reconstructed, not verbatim.
